GridWise — How to Run and Manually Test
======================================

This is a FastAPI service that turns operator notes into a 24-hour battery
solar+grid schedule. The LLM is normally used to interpret notes, but a
deterministic "stub" interpreter is also provided so the project runs
offline. The public sample cases (10 scenarios) are used by the
replay-based test harness to score correctness.

------------------------------------------------------------
1. PREREQUISITES
------------------------------------------------------------
- Python 3.10 or newer (developed against Python 3.13)
- pip
- The bundled requirements.txt:
    fastapi
    uvicorn[standard]
    pydantic >= 2
    pulp        (MILP solver)
    httpx
    python-dotenv
    pdfplumber  (only needed to re-read the spec PDFs)

Install once:
    pip install -r requirements.txt

If you prefer Docker, a Dockerfile and docker-compose.yml are also
included; see "DOCKER" below.

------------------------------------------------------------
2. PROJECT LAYOUT
------------------------------------------------------------
  app/
    main.py              FastAPI entry point
    config.py            settings (env-driven)
    models.py            Pydantic request/response schemas
    guardrails.py        LLM output validation
    llm_interpreter.py   LLM providers + deterministic stub
    optimizer.py         PuLP-based MILP optimizer
    validator.py         final response validation
  tests/
    replay_public_cases.py   runs the 10 public sample cases
  BUP_CSE_FEST_2026_Preli_Public_Sample_Cases.json
                        the 10 reference scenarios + expected outputs
  Dockerfile, docker-compose.yml, requirements.txt

------------------------------------------------------------
3. CONFIGURATION
------------------------------------------------------------
Configuration is read from environment variables (a .env file works too,
via python-dotenv). Important knobs:

  GRIDWISE_LLM_PROVIDER  one of: stub (default), openai, anthropic, google
  LLM_API_KEY            API key for the chosen provider
  GRIDWISE_LLM_MODEL     model name (default gpt-4o-mini)
  GRIDWISE_SOLVER_TIME_LIMIT   seconds (default 15)
  GRIDWISE_TOL           numeric tolerance (default 0.01)
  GRIDWISE_LOG_LEVEL     INFO, DEBUG, etc.

For manual testing, the stub provider is fine. To use a real LLM, set
GRIDWISE_LLM_PROVIDER to a non-stub value and provide LLM_API_KEY.

------------------------------------------------------------
4. RUNNING THE API
------------------------------------------------------------
Local (PowerShell or bash):
    $env:PYTHONPATH = "."
    uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload

Then open:
    http://127.0.0.1:8000/health         -> {"status":"ok"}
    http://127.0.0.1:8000/docs           -> interactive Swagger UI
    http://127.0.0.1:8000/redoc          -> ReDoc API reference

The single optimization endpoint is:
    POST /optimize-energy
    Content-Type: application/json

Docker (alternative):
    docker compose up --build
Then the same URLs work on http://127.0.0.1:8000.

------------------------------------------------------------
5. REQUEST SHAPE
------------------------------------------------------------
The body must be a single scenario. Minimal example:

    {
      "scenario_id": "demo-01",
      "operator_notes": [
        "Facilities will wash the rooftop solar panels from noon until 2 PM. \
         During cleaning, usable solar should be treated as roughly 25% \
         of the forecast."
      ],
      "hours": [
        {"hour": 0,  "demand_kwh":  90, "solar_kwh":   0, "tariff_bdt_per_kwh":  6},
        ... 23 more entries for hour 1..23 ...
      ],
      "battery": {
        "capacity_kwh": 220,
        "initial_energy_kwh": 110,
        "minimum_energy_kwh": 40,
        "max_charge_kwh_per_hour": 50,
        "max_discharge_kwh_per_hour": 50
      }
    }

Hard rules (the API returns HTTP 400 if any are broken):
- 24 unique entries for hours 0..23 in ascending order.
- All kWh / tariff values are non-negative.
- initial_energy_kwh must be inside [minimum_energy_kwh, capacity_kwh].
- operator_notes must be a non-empty list of non-empty strings (max 10).

------------------------------------------------------------
6. RESPONSE SHAPE
------------------------------------------------------------
A successful POST returns:
    scenario_id               echoes the request
    directive_interpretation  one entry per operator_note:
                              {note_index, applies, directive_type,
                               structured_adjustment, explanation}
    hourly_plan               24 rows:
                              {hour, grid_kwh, solar_used_kwh,
                               battery_action (charge|discharge|idle),
                               battery_kwh, battery_energy_after_kwh}
    total_grid_kwh            sum of grid_kwh
    total_cost_bdt            sum(grid_kwh * tariff_bdt_per_kwh)
    peak_grid_kwh             max(grid_kwh) over the 24 hours
    plan_summary              human-readable summary

Six directive types are recognized:
  solar_reduction        structured_adjustment.hours + factor (0..1)
  no_charge_window       structured_adjustment.hours
  no_discharge_window    structured_adjustment.hours
  max_grid_window        structured_adjustment.hours + max_grid_kwh
  minimum_battery_reserve structured_adjustment.hours + minimum_energy_kwh
  no_op                  applies=false, structured_adjustment=null

Notes the stub does not recognize are returned as no_op.

------------------------------------------------------------
7. ERROR RESPONSES
------------------------------------------------------------
HTTP 400  malformed_request     - body failed Pydantic validation
         invalid_directive     - LLM output failed guardrails
HTTP 422  infeasible_scenario   - the MILP could not satisfy the constraints
HTTP 500  llm_unavailable       - all LLM retries failed
         internal_consistency  - optimizer output failed post-validation
         internal_error        - anything else

------------------------------------------------------------
8. WHAT TO LOOK FOR DURING MANUAL TESTING
------------------------------------------------------------
The test harness already exercises 10 reference scenarios. When you run
it, watch for:

  python tests/replay_public_cases.py
      -> prints PASS/FAIL per scenario; expects 10/10.

A scenario is considered PASS only if BOTH conditions hold:
  (a) directive_interpretation matches the reference semantically
      (note_index, applies, directive_type, hours, and any
      factor / minimum_energy_kwh / max_grid_kwh within 0.01),
  (b) total_cost_bdt is within 0.01 BDT of the reference,
      total_grid_kwh within 1 kWh, peak_grid_kwh within 0.5 kWh.

Manual test ideas (use the sample JSON as a template):
  - Single directive, no distractor     (SAMPLE-01, SAMPLE-09).
  - Distractor note that should be no_op
    (SAMPLE-01, SAMPLE-06, SAMPLE-10).
  - Percentage-based reserve
    ("at least 50% of the battery capacity")  -> SAMPLE-03.
  - Worded grid cap
    ("must not exceed", "limit is", "stay at or below")  -> SAMPLE-05,
    SAMPLE-07, SAMPLE-10.
  - Conflicting-charge/discharge windows in the same scenario
    (SAMPLE-08).
  - Multiple constraints stacked  -> SAMPLE-07, SAMPLE-10.

When you POST a scenario, sanity-check:
  - All 24 hourly rows are present and in hour 0..23 order.
  - battery_energy_after_kwh for hour 23 equals initial_energy_kwh
    (end-of-day neutrality).
  - battery_energy_after_kwh never goes below the active minimum
    (battery.minimum_energy_kwh, raised by any
    minimum_battery_reserve directive).
  - grid_kwh is never negative.
  - For hours inside a max_grid_window, grid_kwh <= max_grid_kwh.
  - For hours inside a no_charge_window, battery_action is never
    "charge".
  - For hours inside a no_discharge_window, battery_action is never
    "discharge".
  - For hours inside a solar_reduction window, solar_used_kwh is
    bounded by solar_kwh * factor.
  - Energy balance holds each hour:
       grid_kwh + solar_used_kwh + discharge
         == demand_kwh + charge
  - total_cost_bdt == sum(grid_kwh * tariff_bdt_per_kwh).
  - peak_grid_kwh == max(grid_kwh).

If you want a quick API smoke test, you can also run the bundled
helper scripts:
    python _e2e.py            # POSTs every public case and prints
                              # a side-by-side cost/grid/peak table.

------------------------------------------------------------
9. RUNNING THE TEST SUITE
------------------------------------------------------------
PowerShell:
    $env:PYTHONPATH = "."
    python tests/replay_public_cases.py

Bash:
    PYTHONPATH=. python tests/replay_public_cases.py

Optional flags:
    --cases <path>   alternative sample-case JSON file
    --case SAMPLE-04 run a single scenario
    --url http://...  validate a live server instead of the in-process app

Expected output ends with: "Summary: 10 pass, 0 fail".

------------------------------------------------------------
10. TROUBLESHOOTING
------------------------------------------------------------
- "LLM provider failed after N retries"
  -> Real LLM provider selected but no/invalid API key. Either set
     LLM_API_KEY or switch GRIDWISE_LLM_PROVIDER=stub.

- "Optimizer status: Infeasible"
  -> The combination of constraints cannot be satisfied (e.g. a
     minimum_battery_reserve that exceeds battery capacity, or a
     window that disallows both charging and discharging while the
     initial charge is too low). The API returns HTTP 422.

- Total cost diverges from the reference
  -> Make sure you are using the stub interpreter for deterministic
     outputs. With a real LLM, expect small drift.
  -> Confirm the LLM provider is set to "stub" (or your provider
     returns the same directives as the reference).

- PuLP / CBC not found
  -> pip install pulp (re-try). The optimizer uses the bundled CBC
     solver; no extra install is needed beyond pulp itself.

------------------------------------------------------------
11. END-TO-END SMOKE TEST
------------------------------------------------------------
With the API running on http://127.0.0.1:8000:

    curl -X POST http://127.0.0.1:8000/optimize-energy ^
         -H "Content-Type: application/json" ^
         --data-binary @BUP_CSE_FEST_2026_Preli_Public_Sample_Cases.json

(For only one scenario, extract cases[0].input from the JSON file.)

You should receive a 200 with a directive_interpretation, a 24-row
hourly_plan, and the totals (total_grid_kwh, total_cost_bdt,
peak_grid_kwh, plan_summary) — all matching the reference for that
scenario.
